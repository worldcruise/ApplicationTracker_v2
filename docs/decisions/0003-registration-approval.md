# Public registration with administrator approval

Accepted direction: user request, 21 October 2026. Implements design §§4–5 and 8, with the explicit onboarding change below.

The original design/build-plan D10 proposed invite-only onboarding. The user now explicitly requests public email/password registration followed by administrator approval. This supersedes the invite-only restriction for configured account intake; the original design and PRD remain faithful source records. Trusted invitations and controlled first-admin bootstrap remain available.

- A trusted operator configures one existing active intake organization in private database configuration. No browser-supplied organization, role or team metadata controls admission. Registration is unavailable until configured; no first registrant becomes Admin.
- An Auth INSERT trigger creates one pending request per new, non-invited identity in the same Auth transaction. Full name and email are frozen applicant claims, not verified candidate facts. Configured intake applies even if callers omit the form's flow marker. Existing users are not backfilled or demoted. Trusted invitations retain their existing activation workflow.
- Email confirmation and Admin approval are independent. Approval requires current confirmed Auth email. No pending/rejected identity resolves an application role, even if an old provisioning path accidentally creates membership. Existing identities without public requests keep their current membership behavior.
- Applicants can call only their own status projection, without supplying a user ID. Raw requests and current email/verification state are visible only to current Admins of the request's frozen organization. The Admin projection shows current Auth email alongside the frozen registration email when different, avoiding a stale verification label after an email change. Auth reads use narrow fixed private bridges, never browser or ordinary-query service keys.
- Any current organization Admin may approve an applicant as one of the four roles. Non-Admin roles require an active same-organization team; Admin is organization-wide without a team. Self-review is forbidden. Only controlled bootstrap creates the initial administrator.
- Review takes the existing organization lock, locks the request, validates its row version, and atomically creates active user/organization/team records, records the final decision and appends an audit event. Identical final-payload retries return the original version without rewriting reviewer/time or duplicating audit. Opposing decisions return conflict. Final decisions cannot be edited through this command; mistaken rejection needs a later explicitly designed reconsideration workflow, not an UPDATE or new signup.
- Names/emails are minimal admission records, retained with immutable decision and audit history; no automatic Auth deletion/purge is added. Changing the intake organization affects future requests only. Disabling intake does not erase pending requests or revoke previously approved users.

Reference patterns checked against current official [Supabase signup](https://supabase.com/docs/reference/javascript/auth-signup), [managed user data/trigger guidance](https://supabase.com/docs/guides/auth/managing-user-data), [SSR client documentation](https://supabase.com/docs/guides/auth/server-side/creating-a-client), and [CLI email-confirmation configuration](https://supabase.com/docs/guides/local-development/cli/config). A failed Auth trigger fails signup; deploy/test the migration before opening hosted intake.
